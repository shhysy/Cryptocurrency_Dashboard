## 3. 测试要求

1. **参数测试：** 对积极型/保守型配置逐项断言，特别检查A2、B2、C2、D2、E2覆盖值。
2. **策略纯逻辑：** 评分、企稳、BTC市场状态、头仓、补仓、备用金、止盈、底仓和追踪止损。
3. **订单状态机：** pending、claimed、submitted/unknown、reconcile_required、partial fill及终态。
4. **成交账本：** 仅确认成交入账；重复fill幂等；冲突记录拒绝并进入人工复核。
5. **数据质量：** 未收盘周线、时间戳错位、关键字段缺失、NaN/Infinity、重复/乱序K线和缓存过期。
6. **浏览器持久化：** 多标签页并发、重启恢复、事务中止、升级阻塞和存储配额耗尽。
7. **安全与界面：** LIVE关闭、密钥不进入浏览器、信号价/执行价区分、STALE标记和许可拒绝原因。
8. **回测：** 分资产形态、样本外、成本敏感性、退市样本及定投/买入持有基准。

## 4. 验收与上线边界

- 测试与TypeScript检查通过，只能说明当前自动化检查通过，不等于策略已完成回测。
- 订单提交结果未知时必须对账/人工复核，不得盲目重发。

## 7. 本轮补充核对结论

- **追踪止损峰值：** 原实现使用周线收盘价 `c` 计算峰值，可能低估周内最高价；现改为买入后已收盘周线的最高价 `h` 与当前价取最大值。
- **自动执行数据许可：** 看板开始刷新时先撤销许可；刷新失败、数据标记STALE、非Binance来源、账户未知或快照时间超过120秒，均不允许新订单。只读订单对账与通知处理不因此停止。
- **CI证据：** 本轮核心策略及回归测试在提交 `a0d419b800f1df0d91d7501cec20cac850085e76` 对应的CI中通过（Run 44695407917）；后续仅追加快照许可的年龄检查，仍需确认最新提交CI。


## 8. 山寨币组合数量上限边界修复（2026-11-20）

- 核查发现：`planBuy` 原先以 `findHead(...) !== null` 判断是否已有该币持仓，再决定是否占用山寨币新增名额；但 `findHead` 使用头仓金额门槛，而看板的 `altHeldCount` 按实际非尘埃持仓统计。已有小额持仓可能被统计为组合中的一个山寨币，却因尚未达到头仓门槛被误判为新币，从而在组合数量达到3时阻断对同一币种补足头仓。
- 修复：头仓识别仍由 `findHead` 决定；组合新增名额只在 `input.qty <= 0`（当前无实际持仓）时检查。未改变 `altMaxCount=3`、头仓门槛或任何策略参数。
- 回归测试：保留“无持仓且已有3个山寨币时阻断新开”的测试；新增“已有小额UNI持仓且组合计数为3时，不因补足该币头仓而重复占用名额”的测试。
- 提交：代码 `9857136660c56fd7a3a7f83f2d8b1cc929042da1`；测试 `6406613b443d2265806dfc7563c295b1e334eaba`。
- CI：测试提交对应 Run `44697343391`，记录时仍在运行；代码提交对应 Run `44697325336`，记录时仍在运行。最终验收以测试提交CI结论为准。
- 边界：此修复仅处理策略引擎中是否新开币种的判断；交易执行前仍需以账户快照和真实持仓预检为准。尚未完成真实浏览器/测试网演练。
