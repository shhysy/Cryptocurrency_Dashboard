# 策略3.3服务端自动执行架构设计（实施跟踪）

> 状态：基础设施代码已进入开发分支，尚未部署；尚未接入真实订单执行器，未启用任何真实订单。  
> 目标：消除浏览器页面存活依赖，为BUY/SELL提供服务端持久化队列、账户级互斥、订单对账和故障恢复。  
> 策略参数唯一来源仍为根目录 `策略3.3.xlsx`；本文件只定义执行基础设施，不改变策略参数。

## 1. 当前架构的边界

当前项目使用 Next.js + OpenNext Cloudflare Worker。看板中的 `ExecutionBackground` 依赖页面挂载和浏览器可见状态；BUY/SELL队列、资金预留及成交台账仍有 IndexedDB 本地状态。因此：

- 关闭浏览器、设备休眠或页面不活跃时，不保证继续运行。
- IndexedDB只能协调当前浏览器存储，不是跨设备账户级资金锁。
- 服务端 Spot 下单路由已经提供环境隔离、独立方向开关和下单前二次预检；Durable Object SQLite基础表、内部幂等订单意图落库入口及Cron看门狗代码已加入开发分支，但尚未部署，也未接入Next.js策略事件和Binance执行器。
- 本设计不把当前系统描述为已完成无人值守自动交易。

## 2. 目标架构

采用“OpenNext自定义Worker入口 + 每个交易账户一个Durable Object协调器 + SQLite持久化状态 + DO Alarm调度 + Cron看门狗”的结构。

```text
Next.js Dashboard / Strategy Engine
             |
             | 同源、认证的订单意图请求
             v
OpenNext Custom Worker
  - fetch: 转发给 .open-next/worker.js
  - scheduled: 周期性唤醒账户协调器
  - exports: ExecutionAccountDO
             |
             v
ExecutionAccountDO（按交易账户稳定命名）
  - SQLite订单意图/attempt/fill/reservation/audit
  - 账户级活动订单锁
  - leaseToken + attempt fencing
  - 唯一幂等键与状态机
  - alarm(): 到期对账/退避重试/通知派发
             |
             v
Binance Server Adapter
  - 环境/方向开关
  - 交易对过滤器与余额预检
  - clientOrderId
  - 订单查询与逐笔成交对账
             |
             v
Binance Spot API（开发阶段只允许Mock/Spot Testnet）
```

## 3. Cloudflare组件职责

### 3.1 OpenNext自定义Worker入口

当前 `wrangler.jsonc` 的入口是 `.open-next/worker.js`。OpenNext生成的Worker只导出fetch；要增加Cron的 `scheduled()` 和自定义Durable Object导出，需要增加受版本控制的自定义Worker入口，并在其中复用生成Worker的fetch handler。

建议：
- 新建 `worker.ts`，导入 `.open-next/worker.js`，将HTTP请求转发给其fetch。
- 在同一入口增加 `scheduled(controller, env, ctx)`。
- 导出 `ExecutionAccountDO` 类。
- 将 `wrangler.jsonc` 的 `main` 指向 `worker.ts`。
- 保留现有 `WORKER_SELF_REFERENCE` 服务绑定；不得编辑构建生成的 `.open-next/worker.js`。

当前已完成：`worker.ts` 转发OpenNext fetch、导出 `ExecutionAccountDO`，并由 `scheduled()` 每分钟向账户DO发送内部看门狗心跳；`wrangler.jsonc` 已配置DO绑定、SQLite迁移和Cron。该Cron目前只写入心跳并安排DO Alarm，不扫描或执行交易任务。配置尚未部署，必须通过 `npm run build:cf` 与Wrangler本地预览验证后才可部署。

### 3.2 Durable Object + SQLite

每个Binance交易账户映射到稳定的DO名称，例如 `binance-spot-primary`。不要把API Key、Secret或用户敏感信息放进DO名称。

DO基础类 `lib/execution/execution-account-do.ts` 已创建以下SQLite表，并提供内部订单意图幂等落库和审计写入。当前只有意图落库、看门狗心跳和健康查询可用；attempt、reservation、fill、scheduler_tasks目前只有schema，尚无完整读写业务与原子claim实现。

| 表 | 关键字段 | 用途 |
|---|---|---|
| `order_intents` | intent_id、strategy_event_id、symbol、side、quote_amount、state、created_at | 策略订单意图与幂等 |
| `order_attempts` | attempt_id、intent_id、client_order_id、lease_token、state、exchange_order_id、started_at | 每次外部提交尝试与fencing |
| `reservations` | reservation_id、intent_id、asset、amount、consumed_amount、state | USDT/基础资产预留 |
| `fills` | symbol、trade_id、order_id、qty、quote_qty、commission、commission_asset、filled_at | 交易所成交真源，trade_id唯一 |
| `audit_events` | audit_id、intent_id、attempt_id、event_type、payload_hash、created_at | 状态变更审计，不记录密钥 |
| `outbox` | event_id、payload、state、lease_token、lease_until、attempts、next_attempt_at | 通知及下游事件至少一次投递 |

SQLite事务只负责本地状态原子更新；不得在数据库事务中等待Binance网络请求。

### 3.3 调度

- 目标由DO Alarm负责单账户内最近到期任务：订单对账、退避重试、过期租约清理、Outbox派发。当前Alarm仅记录触发时间，尚未执行任务分派。
- 每个DO只有一个Alarm；在SQLite中保存所有待执行任务，Alarm始终指向最近到期任务，执行后再安排下一次。
- Worker Cron配置为每分钟唤醒账户DO写入看门狗心跳；当前尚未实现逾期任务扫描，不能据此宣称后台订单执行已完成。
- 所有调度按至少一次执行设计，重复唤醒必须安全；依靠intent幂等键、fill唯一键、leaseToken和状态机防重。

## 4. 订单执行状态机

建议订单意图状态：

`queued → preflight → reserved → submitting → submitted/unknown → reconciling → partially_filled/filled/canceled/expired/rejected`

关键规则：

1. 创建订单意图时用确定性 `intent_id` 防止重复策略事件。
2. 在DO事务内检查策略版本、方向开关、固定额度、白名单、单币成本上限、持仓数量限制及账户活动订单锁。
3. 在提交前持久化 `attempt_id`、唯一 `clientOrderId`、`leaseToken` 和 `submitting` 状态。
4. 网络POST只能执行一次。超时或响应不明一律进入 `unknown/reconciling`，按 `clientOrderId` 查单；禁止直接生成新attempt重发。
5. 订单查询与逐笔成交查询必须完成累计数量、累计金额、tradeId唯一性、手续费资产及数量精度核对。
6. 只有交易所确认的fill能更新持仓、成本、已执行止盈档位和资金预留消耗。
7. 只有交易所订单进入终态且fill对账完整后，才能释放未成交预留或创建下一次attempt。
8. SELL普通止盈/追踪止损仍只能使用周期仓；底仓减仓必须按策略3.3和已确认成交账本重新计算保护量。
9. 未知状态、数据冲突、超量成交、缺失fill或账本不一致进入人工复核，不自动猜测。

## 5. 并发、租约与fencing

- 一个账户DO统一协调该账户所有币种的订单意图和资金预留；同一账户不允许并发越过账户级USDT/基础资产余额限制。
- DO事务中完成“检查余额快照版本 + 统计活动预留 + 创建预留 + 领取attempt”。
- 每次领取生成单调递增attempt和随机leaseToken；所有后续状态写入必须同时匹配intent、attempt和leaseToken。
- 租约过期只允许新调度器接管对账，不允许旧调度器把已接受订单覆盖为failed。
- 外部Binance不识别内部fencing token，因此一旦进入 `submitting/unknown`，即使租约过期也只能对账，不得重新POST。
- 不宣称网络严格exactly-once；目标为至少一次调度 + 幂等状态效果 + 不确定提交冻结。

## 6. API与安全边界

- 浏览器只提交策略事件引用或读取状态；不允许浏览器自行决定任意symbol、金额和side并直接下单。
- 服务端重新加载可信策略配置、行情快照、账户快照与持仓台账，重新计算订单意图。
- 服务端API继续要求认证、同源保护、请求大小限制、限流和审计；DO只允许通过Worker绑定调用，不暴露公共写入端点。
- Binance Secret只存在Worker Secret中；生产Key最小权限，禁止提现/划转。
- Testnet/Production环境和BUY/SELL方向开关四路隔离；所有生产开关默认关闭。
- 生产模式不得由“存在真实Key”自动开启，必须同时满足显式环境与服务端方向授权。
- Simple Earn赎回单独作为后续阶段，不与Spot订单共用未经审查的执行路径。

## 7. 故障恢复与告警

- Worker/DO重启后从SQLite恢复未完成intent、attempt、reservations和outbox。
- POST前崩溃：若状态已持久化为submitting，恢复时按clientOrderId查单，不盲目重发。
- POST后响应丢失：标记unknown，按clientOrderId查询订单与成交。
- 订单仍NEW/PARTIALLY_FILLED：继续对账并保持活动锁。
- 租约过期：新调度器接管对账；旧token写入全部拒绝。
- 账本冲突或超出可验证范围：进入manual_review并通知用户，停止该账户新订单。
- Outbox按至少一次投递，使用稳定event_id和接收端幂等键；不声称网络exactly-once。
