# 运维手册（本地常驻交易）

面向使用者，不涉及改代码。

## 1. 安装

1. 安装 Node.js 22 LTS
2. 克隆仓库并进入目录
3. 执行：

```bash
npm install
cp .env.example .env.local
```

## 2. 填写配置

编辑 `.env.local`（不要提交到 Git）：

| 变量 | 说明 |
|------|------|
| `AUTO_TRADE_MODE` | `off` / `dry-run` / `testnet` / `production`，默认 `off`；Trader的Testnet BUY/SELL授权和Binance环境由此派生 |
| `BINANCE_SPOT_ENVIRONMENT` | `testnet` 或 `production` |
| `BINANCE_TESTNET_API_KEY` / `SECRET` | 测试网密钥 |
| `BINANCE_API_KEY` / `SECRET` | 实盘密钥（仅生产） |
| `I_UNDERSTAND_LIVE_TRADING` | 生产必须为 `yes` |
| `TRADER_POLL_INTERVAL_MS` | 轮询间隔，默认 15000 |
| `TRADER_CIRCUIT_FAILURES` | 连续失败熔断阈值，默认 5；只触发停机保护，不限制策略交易金额/次数 |
| `TRADER_DB_PATH` | 默认 `data/trader.db` |
| `TRADER_LOCK_PATH` | 默认 `data/trader.lock` |
| `TRADER_STATUS_API_ENABLED` | 本地Trader状态只读接口，默认 `0`；仅本机回环访问时设为 `1` |
| `TRADER_LOG_DIR` | 默认 `data/logs`，按UTC日期生成日志文件 |
| `SMTP_HOST` / `SMTP_PORT` | QQ邮箱使用 `smtp.qq.com` / `465`（SSL）；模板已填写服务器地址和端口 |\n| `SMTP_USER` / `SMTP_PASS` | 发件QQ邮箱地址和QQ邮箱授权码（不是邮箱登录密码）；只写入本机 `.env.local`，不要提交 |\n| `MAIL_FROM` / `MAIL_TO` | 发件地址（通常与SMTP_USER相同）和接收提醒的邮箱地址 |\n| `MAIL_AUTO` | 策略分数邮件，默认自动；设为`0`关闭。Trader处于dry-run/Testnet且行情为真实Binance非STALE时检查55/75分门槛 |\n| `MAIL_MIN_SCORE_CORE` / `MAIL_MIN_SCORE_ALT` | 核心/山寨信号邮件门槛，默认55/75；这是邮件提醒阈值，不是实际BUY许可阈值 |\n| `MAIL_COOLDOWN_HOURS` | 同一币种邮件冷却小时数，默认24 |
| `TRADE_FILL_MAIL_ENABLED` | 买入/卖出成交邮件开关；配置SMTP后设为 `1`，仅Binance确认真实fill后发送 |
| `TRADER_ALERT_MAIL_ENABLED` | Trader连续故障熔断告警邮件，默认 `0`；独立于成交邮件，配置SMTP并验证收件地址后设为 `1` |

## 3. 启动看板

```bash
npm run dev
# http://localhost:3000
```

看板看信号与持仓，不负责无人值守下单。

## 4. 启动 Trader

```bash
# 先用无下单模式检查本地Trader能否正常启动
AUTO_TRADE_MODE=dry-run npm run trader
```

策略分数邮件由Trader主循环自动触发，不需要另开`npm run notify`进程；当Trader为`off`时不扫描信号邮件，使用`dry-run`或`testnet`且SMTP已配置后才检查真实Binance非STALE信号。买入/卖出成交邮件只在Binance确认真实成交后发送。QQ邮箱使用`smtp.qq.com:465`，`SMTP_PASS`填写QQ邮箱授权码；收件地址通过`MAIL_TO`配置。\n\n完成本地检查后，如需进行真实交易所接口演练，在`.env.local`填入专用Binance Spot Testnet Key/Secret、确认提现权限关闭，再启动：

```bash
AUTO_TRADE_MODE=testnet npm run trader
```

Testnet模式会在测试网真实提交BUY/SELL订单（不使用真实资金），不是dry-run。运行前确认`data/STOP`不存在、账户有测试网USDT，并保留Trader日志和订单号用于验收。当前production模式仍由代码硬拒绝，禁止把`AUTO_TRADE_MODE`改成`production`。

- 锁：`data/trader.lock`（禁止双开）
- 库：`data/trader.db`
- 生产模式在验收完成前会拒绝启动

## 5. 紧急停机

```bash
mkdir -p data && touch data/STOP
# 或 Ctrl+C
```

删除 `data/STOP` 后下一轮才恢复新单（仍受模式约束）。

## 6. 排查

| 现象 | 处理 |
|------|------|
| 无法获取锁 | 是否已有 trader；检查 lock 文件 |
| Testnet 拒绝启动 | 环境、BUY/SELL开关、Key、现货交易权限、提现权限、USDT余额响应或服务器时间 |
| 成交通知未发送 | 检查 `TRADE_FILL_MAIL_ENABLED=1`、SMTP主机/端口/账号/授权码及 `MAIL_TO`；查看Outbox重试/人工复核记录 |
| 熔断告警未发送 | 检查 `TRADER_ALERT_MAIL_ENABLED=1`、SMTP配置和收件地址；故障告警先持久化入Outbox，SMTP失败会退避重试，达到10次转人工复核 |
| 本轮失败不重发 | 正常：未知订单只查单 |

熔断邮件仅在连续失败达到 `TRADER_CIRCUIT_FAILURES` 阈值后产生。Trader会先写入 `data/STOP`，再将脱敏后的告警写入SQLite Outbox；邮件发送失败不会反过来中断交易循环，也不会清除STOP。恢复交易前必须先排查日志、订单未知状态和人工复核项。

## 7. 安全

- Testnet/生产启动会实际检查现货交易权限开启、提现权限关闭、USDT余额与服务器时间；生产Key必须关闭提现权限
- 不要提交 `.env.local`
- 未验收前不要 `AUTO_TRADE_MODE=production`


## 紧急停机与订单恢复

- 紧急停机：在项目根目录创建`data/STOP`文件。Trader将停止生成新买卖信号和提交新订单。
- STOP期间不会取消交易所已有订单；Trader继续使用原`clientOrderId`只读查询已有BUY/SELL订单，并核验已发生的成交。
- 删除`data/STOP`只表示允许后续策略扫描恢复；不会重发此前结果未知的订单。未知订单必须先完成原单对账。
- 行情数据STALE时禁止创建新订单，但仍允许对已有订单进行只读恢复。
- 如果SQLite、交易所查单或成交明细无法核实，相关订单保持待对账/人工复核，不得手动删除数据库记录来“清空状态”。



## 8. 本地Trader真实状态看板（可选）

执行看板已改为读取本机Trader的SQLite状态快照，不再把浏览器IndexedDB当作常驻Trader的真实订单状态。

1. 在`.env.local`中设置`TRADER_STATUS_API_ENABLED=1`。
2. 在项目目录启动看板，明确绑定回环地址：

```bash
npm run dev -- --hostname 127.0.0.1
```

3. 浏览器只访问`http://127.0.0.1:3000`；另开一个终端，在同一项目目录启动Trader：

```bash
npm run trader
```

4. 看板每15秒读取一次`data/trader.db`、`data/trader.lock`和`data/STOP`。接口使用SQLite只读连接；数据库不存在时只显示“尚未创建”，不会创建空库或执行迁移。

**安全要求：** 不要把Next.js绑定到`0.0.0.0`，不要通过公网反向代理、隧道或Cloudflare暴露`/api/trader-status`。接口默认关闭，并拒绝带有反向代理转发头的请求。若页面通过公网域名访问，该接口应保持关闭；本地状态数据不会同步到云端。
